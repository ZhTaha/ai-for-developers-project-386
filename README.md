# Календарь звонков

Сервис бронирования тайм-слотов для звонков, по типу [Calendly](https://calendly.com/) / [Cal.com](https://cal.com/). Разработан совместно с ИИ-агентами в рамках курса «ИИ для разработчиков 2.0» (Hexlet) — этап 1 проекта.

## Пользовательский сценарий (по референсу Cal.com)

### Роль владельца (создание типа встречи)

1. Владелец открывает приложение и попадает в свой личный кабинет (админ-часть)
2. Создает **тип встречи**: задаёт название (например, «Звонок по проекту»), длительность (15/30/60 минут), описание и цвет
3. Настраивает **расписание доступности**: дни недели и часы, в которое возможно бронирование
4. Публикует тип встречи — появляется ссылка на публичную страницу бронирования
5. Делится ссылкой с гостем (в сообщении, письме и т.п.)

### Роль гостя (запись на встречу)

1. Гость открывает ссылку на страницу бронирования владельца
2. Выбирает день и свободный слот в календаре (занятые и вне расписания слоты недоступны)
3. Вводит имя, email и комментарий — подтверждает запись
4. Слот блокируется: становится недоступным для повторного бронирования другими гостями
5. Гость видит подтверждение брони на экране

### Результат для владельца

6. Новая запись появляется в списке броней владельца: дата/время, имя и контакты гостя
7. Владелец может просмотреть и при необходимости отменить бронь — слот снова освобождается

## Обязательные функции и ограничения (из задания)

- Создание типа встречи и настройка доступности — без регистрации гостей
- Гость бронируется только в свободный слот; защита от двойного бронирования
- Просмотр списка записей владельцем
- Внешние календари и email-уведомления — **не входят** в задание
- Требования к генерации клиента: API-контракт описан заранее (TypeSpec), клиент генерируется из спецификации

### Правила бронирования

- Интервалы двух записей не пересекаются, даже для разных типов событий
- После брони с 10:00 до 11:00 запись с 10:30 до 11:00 отклоняется
- Запись с 11:00 допустима (примыкающие слотс разрешены)
- Гость видит понятное сообщение о конфликте при попытке занять занятое время

## Суть задачи

Разработать веб-приложение для бронирования календаря по схеме **Design First** — API-контракт проектируется до написания кода:

1. **API-контракт и архитектура** — собираем требования и описываем контракт с помощью [TypeSpec](https://typespec.io/) до первой строки кода
2. **Разработка с ИИ-агентами** — составляем план, декомпозируем задачи и реализуем через агента (в идеале — ни одной строки кода руками)
3. **Функционал приложения** — реализуем ключевые пользовательские сценарии и покрываем их тестами
4. **Интеграционное и E2E тестирование** — проверяем ключевые пути приложения
5. **CI/CD** — непрерывная интеграция и деплой в PaaS (через MCP)
6. **Деплой** — приложение собирается в Docker-образ и запускается в контейнере

## Docker

Приложение упаковано в Docker-образ. Для сборки и запуска:

```bash
# Собрать образ
docker build -t calendar-app .

# Запустить контейнер
docker run -d -p 3000:3000 -e PORT=3000 calendar-app
```

Dockerfile находится в корне репозитория. Образ содержит всё необходимое для работы приложения: Node.js, зависимости, скрипты генерации и TypeSpec контракт.

### Переменные окружения

| Переменная | Значение по умолчанию | Описание |
|------------|----------------------|----------|
| `PORT` | `3000` | Порт, на котором слушает сервер |
| `SLOT_MINUTES` | `15` | Шаг сетки для слотов бронирования |
| `DATA_FILE` | `./data.json` | Путь к файлу с данными |

### Multi-stage Docker build

Проект использует многоступенчатую сборку для оптимизации размера образу:

1. **Builder этап**: Устанавливает зависимости, компилирует TypeSpec в OpenAPI
2. **Runtime этап**: Минимальный образ Node.js с только необходимыми файлами

Образ легче, так как не несет в себе инструментов разработки и исходный код TypeSpec, оставляя только скомпилированный контракт и сгенерированный клиентский SDK.

## Деплой в Render (через MCP)

Приложение можно деплоить на [Render](https://render.com/) — платформе PaaS, которая бесплатно хостит веб-сервисы из Docker-образов.

### Настройка MCP для Render

MCP (Model Context Protocol) сервер для Render позволяет агенту автоматизировать деплой:

1. В репозитории есть проектная конфигурация MCP или безопасный шаблон с инструкцией подключения
2. API-ключ можно получать из переменной окружения `RENDER_API_KEY`
3. Файлы с реальными ключами исключаются из Git, шаблон оставляется в репозитории
4. Вход через OAuth описывается в настройках агента, данные сессии в Git не добавляются

### Процесс деплоя

1. Агент подключается к MCP-серверу Render
2. Агент создаёт веб-сервис, выкатывает Docker-образ
3. Приложение запускается по порту из переменной `PORT` (по умолчанию 3000)
4. Render выдаёт публичную ссылку на сервис
5. Агент проверяет, что приложение отвечает

### Бесплатный тариф

- Бесплатный сервис засыпает после 15 минут без запросов
- Первый запрос после паузы отвечает дольше обычного (Cold Start)
- Достаточно для сдачи проекта

### Деплой на Railway (запасной вариант)

Если Render недоступен, можно использовать Railway с тем же Docker-образом:

1. Та же конфигурация `PORT` переменной
2. Аналогичный процесс деплоя через MCP
3. Публичная ссылка на работающий сервис

### Важное замечание о сохранности данных

**Данные сбрасываются после перезапуска контейнера.**

Хранилище данных основано на JSON-файле `data.json` (путь задаётся переменной `DATA_FILE`). При перезапуске контейнера данныеinitializaeтся из-заданных в коде дефолтных значений:

- Тип встречи по умолчанию: `'intro-call'` (Знакомство, 30 минут)
- Рабочие часы по умолчанию: `weekdays [1,2,3,4,5]`, `startTime '09:00'`, `endTime '18:00'`, `timeZone 'Asia/Almaty'`
- Бронирования инициализируются пустым списком

Для сохранения данных между перезапусками необходимо примонтировать том или использовать внешнюю базу данных:

```bash
docker run -d -p 3000:3000 -v $(pwd)/data.json:/app/data.json -e PORT=3000 calendar-app
```

или через docker compose:

```yaml
services:
  calendar:
    image: calendar-app
    ports:
      - "3000:3000"
    volumes:
      - ./data.json:/app/data.json
    environment:
      - PORT=3000
```

Это помнит настройки owner (типы встреч, рабочие часы, часовой пояс) и сохраняет списки броней. Однако сами ссылки на бронирования гостевского режима не сохраняются долгосрочно из-за природы бесплатного тарифа Render (сервис засыпает и перезапускается).

## Разработка с агентами

Проект предназначен для работы с ИИ-агентами. Спецификация и тикеты находятся в файлах `SPEC_AND_TICKETS.md` и `DECISIONS_MAP.md`. Агенты должны следовать правилам из `AGENTS.md`, включая:

- Коммиты по Conventional Commits
- Ссылки на тикеты в коммитах
- Использование TypeSpec контракта
- Тестирование через всю стек (контракт → SDK → сервер → интерфейс → тесты)
