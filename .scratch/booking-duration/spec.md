# Спека: бронь занимает всю длительность встречи

Status: ready-for-agent

## Problem Statement

Гость бронирует встречу (например, 60-минутный «Звонок по проекту»), но система блокирует только один слот. Остальное время встречи остаётся доступным для бронирования другими гостями — владелец получает наложащиеся встречи и теряет доверие к сервису.

Дополнительно: сетка слотов сейчас 30 минут, а у типов встреч есть 15-минутная длительность; слоты вычисляются только по 30-минутной сетке, поэтому 15-минутные встречи не выражаются аккуратно.

## Solution

Бронь занимает интервал `[slotStart, slotStart + durationMinutes)`. Любой слот, пересекающийся с занятым интервалом, недоступен для бронирования. Начало брони разрешено только на 15-минутной сетке. Слот не обязан целиком укладываться в окно доступности: последняя встреча дня может начаться до конца окна и выйти за его границу — обрезки встреч нет.

## User Stories

1. Как гость, я хочу, чтобы при бронировании 60-минутной встречи блокировались все пересекающиеся слоты, чтобы другой гость не смог записаться на середину моей встречи.
2. Как гость, я хочу видеть занятыми слоты, которые частично пересекаются с существующей бронью, чтобы не попасть в конфликт двойного бронирования.
3. Как гость, я хочу начинать бронь в :00, :15, :30 или :45, чтобы сетка соответствовала 15-минутным встречам.
4. Как гость, я хочу получить понятную ошибку (409), если слот занят или вне расписания, чтобы выбрать другой слот.
5. Как владелец, я хочу, чтобы встреча могла начаться в последний слот дня и выйти за endTime, чтобы не терять последний интервал окна.
6. Как владелец, я хочу, чтобы отмена брони освобождала все пересекающиеся слоты, чтобы время снова стало доступным.
7. Как владелец, я хочу видеть в списке броней длительность каждой брони, чтобы планировать день.
8. Как владелец, я хочу, чтобы существующие брони, сохранённые до этой фичи, продолжали работать, чтобы данные не потерялись.
9. Как владелец, я хочу, чтобы API-контракт (TypeSpec) описывал бронь с длительностью, чтобы клиент соответствовал серверу.
10. Как разработчик, я хочу, чтобы логика занятости ждалась в чистых функциях calendar, чтобы её можно было тестировать отдельно от HTTP.
11. Как разработчик, я хочу, чтобы вычисление слотов использовало 15-минутную сетку, чтобы 15-минутные типы встреч были первоклассными.
12. Как гость, я хочу, чтобы бронь не принималась со slotStart вне 15-минутной сетки, чтобы данные оставались консистентными.

## Implementation Decisions

- Бронь занимает интервал `[slotStart, slotStart + durationMinutes)`. Занятым считается любой слот с ненулевым пересечением с этим интервалом.
- Длительность брони берётся из длительности её типа встречи в момент бронирования и сохраняется в самой брони (поля `durationMinutes` в модели Booking), чтобы отмена типа встречи не ломала вычисление занятости.
- Сетка slotStart — 15 минут (константа слота меняется с 30 на 15). slotStart вне сетки отклоняется с 400.
- Слоты вычисляются по 15-минутной сетке внутри окна доступности; слот не обрезается по endTime последней встречи — пересечение определяется по интервалам, а не по границе окна.
- Бронь не обязана целиком помещаться в окно доступности: требуется только попадание slotStart в окно и на сетку. Пересечение границы дня не рассматриваем (окно в пределах одного дня).
- Старые брони без `durationMinutes` при чтении считаются 15-минутными (обратная совместимость хранилища).
- Сначала обновляется TypeSpec-контракт (`Booking` получает `durationMinutes`), затем сервер и тесты (Design First, требование курса).
- Затрагиваемые модули: контракт (TypeSpec), модуль вычисления слотов/занятости (calendar), HTTP-сервер (валидация slotStart на сетке, сохранение durationMinutes в брони), модуль хранения (дефолт для старых броней).

## Testing Decisions

- Хороший тест проверяет внешнее поведение (статусы ответов, занятость слотов в ответах API), а не внутренние структуры.
- Основной шов — HTTP API: интеграционные тесты через реальный сервер и fetch с изолированным JSON-хранилищем на тест (существующий файл интеграционных тестов API — prior art).
- Дополнительный шов — чистые функции модуля calendar: юнит-тесты на вычисление слотов и проверку пересечения интервалов (кейсы: частичное пересечение, примыкание вплотную, выход за endTime).
- Ключевые кейсы: 60-минутная бронь блокирует 3 последующих слота на 15-минутной сетке; частично пересекающийся слот занят; примыкающий слот свободен; slotStart вне сетки → 400; бронь без durationMinutes = 15 минут.

## Out of Scope

- Отмена брони гостем (сейчас отмена — только владелец).
- Аутентификация и несколько владельцев.
- Email-уведомления и внешние календари (исключены заданием курса).
- Изменение окна доступности больше одного дня.
- Генерация клиента из TypeSpec (отдельный этап курса).
